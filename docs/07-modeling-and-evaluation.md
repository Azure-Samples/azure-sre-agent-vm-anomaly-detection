How the anomaly model that ships in `detector/model/` is built, what data it was trained
and evaluated on, and how to reproduce it. Measured numbers come from `ml/REPORT.md`
(generated by `ml/evaluate.py`); the reasoning behind the model choice is in
`docs/06-modeling-alternatives.md`.

## 1. Purpose

The detector runs every minute and evaluates memory growth, sustained CPU saturation,
and disk fill. Its synthetic evaluation compares detection delay with static
memory thresholds and reports **attribution** (resource group and feature) to
guide SRE Agent triage. These results do not guarantee detection of every VM
anomaly. The model scores the **trend / sustained level** of each
resource group against its own normal range, not absolute levels, and its output is
calibrated so that one fixed threshold (`0.8`) serves every anomaly class in the Azure
Monitor alert rule. The scripted demo incident (a traffic-triggered memory leak) is one
of the anomaly classes it is evaluated on, not the definition of "anomaly".

## 2. Pipeline

```text
datasets ──► make_features(window=30) ──► fit model on normal data ──► calibrate raw score
   │                                                                          │
   └── labelled test series ──► score ──► metrics (F1, PA-F1, delay, false alarms) ──► REPORT.md
                                                                              │
Azure ML job (ml/azureml/job.yaml) ──► register vm-anomaly-detector:N ──► export ──► detector/model/
```

| Step | Tool | Output |
|---|---|---|
| Data | `ml/data/synthetic.py`, `ml/data/smd.py`, `ml/data/nab.py` | `timestamp, <metrics...>, label` frames |
| Features | `ml/features.py` (vendored verbatim into `detector/features.py`) | rolling mean/std/slope/min/max/diff per metric |
| Train + calibrate | `python -m ml.train --dataset ... --model ... --window 30 --out <dir>` | `model.pkl`, `metadata.json` |
| Evaluate | `python -m ml.evaluate --runs <dirs> --report ml/REPORT.md` | metrics tables, `REPORT.md` |
| Azure ML | `python -m ml.azureml.submit` runs `job.yaml` on the `cpu-ds3v2` cluster in `mlw-vm-anomaly` | job outputs `model/` and `eval/` |
| Register | `python -m ml.azureml.register [--job <name>]` | model `vm-anomaly-detector:N` |
| Export | `python -m ml.azureml.export [--version N]` | `detector/model/model.pkl` + `metadata.json` (with `model_sha256`, refused if > 5 MB) |

The Azure ML job trains the shipped synthetic model and, in the same run, the SMD and NAB
evaluation models, then writes `results.md`. Only the synthetic model is registered and
exported; the detector compares the pickle's SHA-256 with `metadata.json` when
present. This catches mismatched files, not a replacement of both by an attacker;
the deployed model must come from the reviewed repository export.

## 3. Datasets

| Dataset | Role | Shape | Labels |
|---|---|---|---|
| **Synthetic live-metric VMs** (`ml/data/synthetic.py`) | **training + primary test set for the shipped model** | simulated 4 GB VM at 1-minute cadence in the six live columns `mem_used_pct, mem_available_mb, swap_used_pct, cpu_pct, disk_used_pct, net_bytes`; diurnal load, CPU bursts, batch jobs, restarts | train: 24 anomaly-free series x 3 days (4,320 min) spanning idle to busy CPU baselines and a range of disk jitter. Test: 4 other seeds x 3 days, each with injected memory leaks (10-20 MB/min, 3-5 h, until restart), a CPU saturation (85-100 % for 30-120 min) and a disk fill (0.2-1 %/min for 30-90 min, log rotation reclaims most of it) = 15 labelled segments (8 leaks, 3 CPU, 4 disk) |
| **SMD** - OmniAnomaly Server Machine Dataset ([source](https://github.com/NetManAIOps/OmniAnomaly/tree/master/ServerMachineDataset)) | real-server sanity check of the feature/model recipe | 38 metrics per machine, 1-minute cadence; 4 machines by default (`--machines`), one model per machine trained on the train split, scored on the labelled test split | provided by the dataset |
| **NAB** `realAWSCloudwatch` ([source](https://github.com/numenta/NAB/tree/master/data/realAWSCloudwatch)) | univariate cloud-metric benchmark (spiky, seasonal) | 17 series, 5-minute cadence, one model per series | `combined_windows.json` anomaly windows |

SMD and NAB are downloaded on first use into the git-ignored `ml/data/raw/`. They use their
own metric columns, so those models are **evaluation evidence only** - the production
live model schema is the six live-metric columns above, which is what the Azure Monitor `Perf`
table provides via the Azure Monitor Agent.

Why synthetic data for the shipped model: there is no labelled anomaly history of
`vm-app-01`, and the anomaly classes we need to detect are known mechanisms (linear memory
growth, a process pinning the CPU, a disk filling up). The simulator injects
those on top of realistic normal behaviour (diurnal load, cron bursts, batch jobs, restarts,
log rotation), giving clean labels for onset time and hence for detection delay per class.

## 4. Features

`make_features(df, window=30)` computes, for every metric, six trailing-window statistics
over 30 rows (30 minutes of live data): `mean, std, slope, min, max` and the first
difference `diff`. The SMD/NAB evaluation models use all of them; the **shipped live model
uses one small feature set per resource group** (`ml/train.py::LIVE_GROUPS`):

| group | features (direction) | what it captures |
|---|---|---|
| `memory` | `mem_used_pct__slope (+)`, `mem_available_mb__slope (-)`, `swap_used_pct__slope (+)` | memory / swap *growing* over the window (leak, runaway allocation) |
| `cpu` | `cpu_pct__min (+)` | the CPU never dropping below a high floor for the whole window (runaway process); bursts and batch jobs do not raise the minimum |
| `disk` | `disk_used_pct__slope (+)` | `/` filling up (log storm, tmp files) faster than normal growth |

Slopes are level-free and the window minimum is compared with the training fleet's range,
so a model trained on simulated VMs transfers to a different VM size. `net_bytes` is still
read by the detector (it is in `input_columns` and reported in the alert `Details`) but is
not a model input: its scale is per-NIC/per-VM and does not transfer without a per-VM
baseline.

Each feature has a **direction** (`+1` = anomalous when large, `-1` = anomalous when small;
`mem_available_mb__slope` is `-1`). Before the forest, a one-sided clip collapses the
harmless side onto the training median (e.g. memory being freed, or a VM that idles lower
than any training VM), so the model cannot fire on recoveries, restarts or "too healthy"
hosts.

## 5. Models compared

| Model | `--model` | Notes |
|---|---|---|
| Isolation Forest (**shipped**) | `iforest` | one sklearn `Pipeline(one-sided clip -> IsolationForest(n_estimators=200))` **per resource group**, each calibrated on its own normal scores; `Score = max` over groups and the winning group is reported in `Details.groups` (`ml/models/iforest.py::GroupedIForestDetector`). A single forest over all features under-scores one-dimensional anomalies (a pinned CPU, a filling disk) because most random splits look at unrelated features. Pooled over all training VMs on the synthetic set; one plain forest per machine/series on SMD/NAB |
| MLP autoencoder | `ae` | reconstruction error; optional Torch dependency |
| Spectral Residual | `sr` | saliency-map baseline from the (retired) Azure Anomaly Detector service |

## 6. Calibration and threshold

Raw anomaly scores are mapped to `[0, 1]` using quantiles of the **normal training** scores:

```text
score = clip(0.8 * (raw - q50) / (q99.9 - q50), 0, 1)
```

so `0.8` corresponds to the 99.9th percentile of normal behaviour **for that group**, i.e.
about 1.4 false points per day per VM per group before any alert smoothing. The per-group
`q50`, `qhi`, `anchor` are stored in `metadata.json["groups"][<group>]["calibration"]`; the
top-level `calibration` is the identity map (group scores are already on the `[0, 1]`
scale) so the detector's formula is unchanged. Per-feature quantiles (`feature_stats`) let
the detector report `TopFeature` and per-feature contributions.

Production alerting adds a second layer: the Azure Monitor scheduled-query rule fires only
when `Score >= 0.8` in **3 of the last 5 minutes** (any group), and a memory-only static
alert (`mem_available_mb < ~200`) remains as a safety net / lateness comparison.

## 7. Evaluation metrics

Computed by `ml/evaluate.py` per run and per series:

* **Precision / recall / F1** - point-wise, at the fixed threshold.
* **PA-F1** - point-adjusted F1 (Xu et al., WWW 2018): a labelled segment counts as fully
  detected if any point in it is flagged. Standard for segment-shaped anomalies.
* **Segments detected** - `detected / total` labelled segments.
* **Mean detection delay** - rows from segment onset to the first flag (1 row = 1 minute on
  synthetic/SMD, 5 minutes on NAB). This is the metric that matters for slow-onset anomalies.
* **False-alarm events** - contiguous flagged runs outside any label, i.e. how often the
  SRE Agent would be paged for nothing.

## 8. Results (from `ml/REPORT.md`)

Synthetic anomalies, 15 segments (8 memory leaks, 3 CPU saturations, 4 disk fills) across
4 test VMs:

| Detector | P | R | F1 | PA-F1 | segments | mean delay (min) | false-alarm events |
|---|---|---|---|---|---|---|---|
| grouped IsolationForest, `score >= 0.80` | 0.983 | 0.892 | 0.935 | 0.992 | 15/15 | 14.2 | 11 |
| grouped IsolationForest + 3-of-5 alert rule | 0.971 | 0.877 | 0.922 | 0.987 | 15/15 | 16.2 | 3 |
| static `mem_used_pct > 90` (memory only) | 0.750 | 0.034 | 0.065 | 0.492 | 4/15 | 174.7 | 0 |
| static `mem_available_mb < 200` (memory only) | 0.750 | 0.006 | 0.012 | 0.492 | 4/15 | 189.2 | 0 |

Findings:

* The grouped Isolation Forest detects all 15 labelled synthetic segments, with a
  mean delay of **14.2 minutes** before alert smoothing and **16.2 minutes** after it.
  The static memory rules detect 4/15 segments, with mean delays near three hours.
  The static rules do not cover CPU or disk anomalies.
* The 3 remaining false-alarm events under the alert rule are all `disk`-group flags on the
  test VM with the noisiest disk jitter; see section 9.
* The autoencoder is close on synthetic data but produces more false-alarm events and adds a
  Torch dependency; Spectral Residual is good at spikes and weak on slow ramps.
* On SMD (PA-F1 0.763, 32/56 segments) and NAB (PA-F1 0.424, 15/30) the fixed-threshold
  Isolation Forest is clearly weaker: those sets are dominated by spike- and drop-type
  anomalies across many unrelated metrics, not slow ramps or sustained floors. They serve as
  a sanity check that the pipeline runs end to end on real data and as a comparison between
  model families, not as a certification of production accuracy.

Exact per-series tables and the SMD/NAB rows are in `ml/REPORT.md`.

## 9. Limitations and calibration

* The shipped model is trained on simulated VMs. Validate per-group score ranges
  against representative, anomaly-free `Perf` history before using it for real alerts.
  Synthetic test results are not a measurement of production generalization.
* The remaining synthetic false alarms come from the noisiest test VM's disk group.
  Training coverage and target-specific baselines affect this behavior; a change
  requires evaluation, not just a new threshold.
* `net_bytes` is included in telemetry but is not a model feature. Per-process
  counters are also outside the shipped model.
* Slower trends and different workload cadences require separate evaluation.
  `--window` is a training parameter stored in `metadata.json`; changing it means
  retraining and exporting a matching artifact.

## 10. Reproduce locally

```bash
uv sync --python 3.11 --extra ml --extra dev
uv run python -m ml.train --dataset synthetic --model iforest --window 30 --out outputs/synthetic-iforest
uv run python -m ml.train --dataset smd --model iforest --out outputs/smd-iforest
uv run python -m ml.train --dataset smd --model sr      --out outputs/smd-sr
uv run python -m ml.train --dataset nab --model iforest --out outputs/nab-iforest
uv run python -m ml.evaluate --runs outputs/synthetic-iforest outputs/smd-iforest outputs/smd-sr outputs/nab-iforest \
    --report ml/REPORT.md
```

For Azure ML, sign in with `az login`, install the `ml` extra, then use
`uv run python -m ml.azureml.submit`, `register`, and `export` as in section 2.
Review the exported artifact and evaluation results before publishing it with
the Function deployment.
